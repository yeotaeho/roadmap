# 개인화 엔진 — 선택적 사용자 데이터 (설계 설명 · 의도 검증)

> **목적** — 이 문서는 "사용자 성향·스펙·기본정보를 받아 개인화 추천을 강화한다"는 요청이 **어떻게 설계·구현됐는지**, 그리고 **원래 의도와 맞는지**를 한눈에 대조하기 위한 것입니다.
> **상태** — Phase 1(데이터층)·2(임베딩 통합)·3(프론트/온보딩) 전부 완료·main 배포됨(커밋 `d885c3a`..`ebe2e4d`). 대화형 추출은 "설계만 준비(미구현)".
> **작성일** — 2026-07-01. 관련: [스펙](superpowers/specs/2026-06-30-user-profile-personalization-design.md) · 플랜 3종([P1](superpowers/plans/2026-06-30-user-profile-personalization-phase1-backend.md)·[P2](superpowers/plans/2026-06-30-user-profile-personalization-phase2-embedding.md)·[P3](superpowers/plans/2026-06-30-user-profile-personalization-phase3-frontend.md)).

## 1. 왜 만들었나 (문제)

진로가 막연한 청년에게 Roadmap은 **Sync**(사용자–트렌드 적합도)·**Chance**(공고 매칭) 추천을 제공합니다. 그런데 이 추천이 쓰던 사용자 정보가 **목표 직무 + 관심 키워드 딱 2개뿐**이었습니다. 즉 "너에게 맞는" 추천을 하기엔 사용자에 대해 아는 게 너무 적었습니다 — 이걸 프로젝트 메모리에서 **"개인화 병목"** 이라 불렀습니다.

이번 작업은 사용자가 **성향·스펙·기본정보**를 (부담 없이·선택적으로) 채우면 그게 추천 품질을 끌어올리도록, **입력 → 저장 → 임베딩 → 추천**의 전체 고리를 완성한 것입니다.

## 2. 당신의 의도 → 설계 반영 (핵심 대조표)

| 당신이 말한 것 | 어떻게 반영했나 | 왜 그렇게 했나 |
|---|---|---|
| "성향, 스펙, 회원가입 기본정보를 받자" | 4개 차원 신설: **기본정보**(나이·성별·지역·상태·학력) · **성향**(작업성향·기업규모·근무형태·가치관) · **스펙**(자격증·어학·링크·프로젝트) · **관심**(직무·산업) | 요청한 세 영역을 데이터 모델로 구체화하고, 추천에 실제로 쓰이도록 배선 |
| "꼭 입력 안 해도 되게, null 허용, **부담 없이**" | 모든 신규 필드 **nullable·선택 입력**. 미입력은 저장 안 함. 회원가입 필수 항목 안 늘림 | 가입·사용 마찰을 늘리지 않기 위해. 채우는 만큼만 개인화가 좋아지는 구조 |
| "**AI 상담실 대화로 데이터를 추출**하는 구조도 생각한 거냐?" | 지금은 폼 입력만 구현. 단 **추출-레디**로 설계 — 모든 테이블에 `source` 컬럼 + 저장 인터페이스가 출처 인자를 받음 | 대화 추출을 나중에 **같은 저장 경로로** 얹을 수 있게. 지금 구현은 범위 밖(별도 작업) |
| "**회원가입에서도, 프로필에서도** 입력 가능하게 (강제 아님)" | 프로필 페이지 선택 섹션 + **로그인 후 1회 온보딩**(건너뛰기 가능). 둘 다 같은 API·컴포넌트 재사용 | 입력 기회를 두 곳에 제공. (원래는 "가입 직후"였으나 실제 로그인 흐름상 토큰이 로그인 후에 생겨서 "로그인 후"로 조정 — 아래 §6 참고) |

> **추가로 내가 내린 판단(당신이 명시하진 않았지만 검토 필요):**
> **데모그래픽(나이·성별·지역)은 추천 임베딩에서 제외**했습니다. 이유는 (1) 성별·나이로 진로를 미는 것은 **편향** 위험이 크고, (2) 이런 값은 "의미"가 아니라 "필터"에 가깝기 때문입니다. 그래서 나이·성별·지역은 저장은 하되 **추천 계산에는 안 쓰고**, 성향·스펙·관심(의미 있는 신호)만 추천에 반영합니다. — 이 결정이 의도와 다르면 알려주세요(향후 "지역 기반 공고 필터" 같은 용도로는 데이터가 이미 쌓입니다).

## 3. 큰 그림 — 3단계 · 풀 루프

```
[사용자 입력]                  [저장]                    [개인화 반영]
프로필/온보딩 선택 섹션   →   user_profiles(기본정보)   →   (추천 제외, 필터용 보관)
 · 기본정보                    user_preferences(성향)   ┐
 · 성향/선호                   user_personas(스펙)      ├→ 임베딩 텍스트로 직렬화
 · 스펙                        user_sync_profiles(관심) ┘   → text-embedding-3-large
 · 관심 분야                                                → user_embeddings(벡터)
                                                              │
                                                              ├→ Sync: 섹터 벡터와 코사인 → 적합도
                                                              └→ Chance: 공고 벡터와 코사인 + 키워드 가산
```

- **Phase 1 (데이터층)** — 테이블·API를 만들어 "받아서 저장"까지.
- **Phase 2 (임베딩 통합)** — 저장된 성향·스펙을 임베딩에 녹여 "추천에 반영".
- **Phase 3 (프론트/온보딩)** — 사용자가 실제로 입력하는 화면.

## 4. 데이터 모델 (테이블 4종, 전부 선택 입력)

| 테이블 | 도메인 | 담는 것 | 추천 반영 |
|---|---|---|---|
| `user_profiles` | auth | 출생연도·성별·지역·현재상태(학생/구직/재직/전환)·학력단계 | ❌ 제외(편향 방지, 필터용 보관) |
| `user_preferences` | user_intelligence | 작업성향(안정/도전/균형)·선호 기업규모·근무형태·일의 가치(다중) | ✅ 임베딩 |
| `user_personas` (확장) | user_intelligence | 기존 스킬·경험·학력 + **자격증·어학·링크·프로젝트** | ✅ 임베딩 |
| `user_sync_profiles` (기존) | auth | 목표 직무 + 관심 키워드 | ✅ 임베딩 |

- 전부 `user_id` 기준, `source` 컬럼 보유(`user_form` / 미래 `coach_extraction`).
- 스키마 변경은 마이그레이션 `a3f7c1e9d2b4` 하나로 Neon 적용 완료.

## 5. 데이터가 추천이 되는 원리 (핵심)

개인화 추천은 **임베딩(embedding) 기반**입니다. 사용자의 의미 있는 정보를 한 줄 텍스트로 합쳐 벡터로 바꾸고, 그 벡터를 섹터·공고 벡터와 **코사인 유사도**로 비교합니다.

- **직렬화**: `직무 + 관심키워드 + 성향(한국어 라벨: "도전 지향", "성장" 등) + 스펙(스킬·자격증·프로젝트명·기술스택)` → 한 줄 텍스트. 데모그래픽은 여기 **안 들어감**.
- **Sync 점수** = 코사인 적합도 60% + 섹터 트렌드(Pulse) 40%.
- **Chance 매칭** = 공고와의 코사인 + 키워드/성향/스펙 용어 직접 일치 가산.
- 즉 **성향·스펙을 채울수록 사용자 벡터가 풍부해지고**, "너와 결이 맞는" 섹터·공고와의 유사도가 정확해집니다.

**중요한 수정 하나 (재임베딩 버그)** — 원래는 한 번 임베딩된 사용자가 나중에 데이터를 바꿔도 **영영 갱신되지 않는** 버그가 있었습니다(신규 사용자만 임베딩). 이번에 "데이터가 바뀌면 다음 일일 배치에서 다시 임베딩"되도록 고쳤습니다(내용이 그대로면 재계산 생략 = 비용 절약).

## 6. 입력 화면 (프론트)

- **프로필 페이지**: 4개 선택 섹션(기본정보·성향·스펙·관심) + **프로필 완성도 미터**("채울수록 추천이 정확해져요"). 각 섹션은 독립 저장.
- **온보딩**: 로그인 후 아직 안 채운 사용자를 `/onboarding`으로 **1회** 안내. "완료" 또는 "나중에 입력" 어느 쪽이든 이후 다시 안 뜸.
- **관심 키워드**: 기존 뉴스 카테고리(경제·정치…) 대신 **12개 산업 섹터 + 직무군**(반도체·바이오헬스·핀테크… / 엔지니어링·데이터·기획…)으로 재설계 — 추천 섹터와 정렬돼 적합도에 바로 기여.

> **왜 "로그인 후" 온보딩인가** — 원래 스펙은 "가입 직후"였습니다. 그런데 실제 코드를 보니 회원가입 완료 시점엔 **토큰이 발급되지 않고 다시 로그인**하는 흐름이라, 인증이 필요한 저장 API를 가입 직후엔 못 씁니다. 그래서 "첫 로그인 후 1회"로 트리거를 조정했습니다. 결과적으로 신규 사용자는 첫 로그인 때 온보딩을 한 번 만나게 됩니다.

## 7. 무엇이 되고, 무엇이 아직인가

**된 것 (라이브)**
- 4차원 선택 데이터 입력·저장(프로필 + 온보딩), 완성도 미터, 키워드 풀 재설계.
- 성향·스펙이 임베딩에 반영 → Sync/Chance 추천에 실제 사용.
- 데이터 변경 시 재임베딩(배치).
- 잘못된 입력 방어(예: 출생연도에 생년월일 8자리 → 안내 후 차단, 서버 500 아님).
- **개인화 1일 지연 해소**(조치됨) — 정제 파이프라인에서 임베딩(`user_embed`)을 `chance_match` 앞으로 옮겨, 같은 회차에서 사용자 벡터를 먼저 갱신 후 매칭. Chance 의미 매칭이 Sync와 동일 시점 반영(커밋 `3787d1a`).
- **반영 지연 단축**(조치됨) — 일일 배치(09:00) 외에 **매시간(HH:30) 경량 새로고침 잡** 추가(`user_embed → chance_match → sync_refine`). 사용자 데이터 변경이 **~1시간 내** 추천에 반영. `user_embed` 해시 스킵으로 변경된 사용자만 재임베딩(저비용). 무거운 Silver 정제는 일일 유지(커밋 `8b4021b`).

**아직 (후속 과제)**
- **대화형 추출(미구현)** — "AI 상담실 대화로 성향·스펙 자동 추출"은 **설계만 준비**됨(`source='coach_extraction'`로 같은 저장 경로 재사용). 실제 추출 로직은 별도 작업.
- **완전 실시간(저장 즉시)은 아님** — 매시간 새로고침으로 지연이 크게 줄었으나, "저장 즉시" 반영은 이벤트 기반(단일 사용자 재점수) 추가 작업이 필요. 현재는 ~1시간 주기.
- 회원가입 화면의 기존 8개 뉴스 카테고리는 이번에 안 바꿈(프로필/온보딩만 신규 풀 사용).

## 8. 검증

- **백엔드**: 엔드포인트 테스트(프로필 12·성향 8·페르소나 13·모델 19) + 임베딩(직렬화 16·재임베딩 7 실모델·Chance 6) + 회귀 = 전부 통과(Neon 실DB).
- **프론트**: `tsc --noEmit` 0 에러(프론트 단위테스트 프레임워크 없음 — 타입+계약 검증).
- **리뷰**: 각 작업 단위 독립 리뷰 + 단계별 종합 리뷰(Opus). Critical/Important 결함 0.

## 9. 한 줄 결론

**"부담 없이 채우는 선택 데이터가, 채운 만큼 추천을 정확하게 만든다"** — 이 고리를 데이터·임베딩·화면까지 완성했습니다. 데모그래픽 임베딩 제외, 대화 추출 레디, 로그인 후 온보딩 — 이 세 가지가 의도와 맞는지 확인해 주시면, 필요 시 조정하겠습니다.
